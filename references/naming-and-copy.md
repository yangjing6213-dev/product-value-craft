# 项目命名、标题与文案

## 先确认这段文字放在哪里

品牌/项目名需要可识别、可检索和适度延展；页面标题需要说明相关任务；推广标题需要让合适的人愿意了解。不要把长宣传口号强行当成项目名。用户已有名字时保留，可增加描述性副标题；注册、商标、域名可用性必须另行核验，候选名字不等于已可合法使用。

复用目标人群、触发时刻、成果、真实能力、必要条件与下一步。已知信息足够时直接写，避免要求用户填写完整营销问卷。

## 从事实写到价值

先确定“支持什么”，再写“在这个场景里帮助完成什么”，最后补“怎么知道以及什么条件下成立”。

例如，已知能力是“导出一份本地项目清单”，可写“交接项目之前，先核对要移交哪些文件”。不能直接升级成“所有资料永不丢失”或“自动完成项目迁移”。用户需要在其他软件完成的步骤应准确说明，不能暗示本产品内置。

遇到购买阻力，选择相应信息：

| 阻力 | 文案需要回答 |
| --- | --- |
| 不适用 | 谁适合、谁不适合、需要什么条件 |
| 决策信息不足 | 交付、流程、费用、权限、支持与限制 |
| 卖点与自己无关 | 具体触发场景、能完成的结果与例子 |
| 担心买错 | 可查看的演示、试用条件、失败边界及真实支持规则 |

## 根据任务选择表达角度

- **任务角度：**正在做什么，下一步怎样更清楚。例如“交接项目之前，先看这份文件清单”。
- **结果角度：**明确可得到的成果，避免没有依据的速度和成功率。
- **对比角度：**比较同一任务、条件与口径，说明真实差异，不贬低用户或未经核实的竞品。
- **情绪角度：**从完成、掌控、表达或减少困惑产生感受；不借羞耻、身份排斥或制造恐惧促单。

动词通常帮助说明动作，但不必禁止名词和形容词。技术词首次出现时给普通解释，保留有检索价值的名称。数字、认证、评价、专家身份只有依据充分时才使用；素材中的示例数字不能移植为自己的证据。

用户要选项时给有实质区别的少量候选，并推荐与其目标最匹配的一项；不要为了“深度”堆十几个近义标题。只要最终文案时直接交付可用版本。

## 常见页面结构

首屏通常包含一条场景/结果主张、一句实现方式、一个与访客阶段匹配的主要动作，以及影响适用性的简短条件。详情页再展开演示、要求、交付、成本、疑问和支持。长度按实际需求决定，不强制凑模块。

按钮描述真实去向：查看示例、检查适用条件、开始创建、获取报价、购买相应产品。不要用“立即免费体验”指向付费页或把下载按钮当成已成功安装。

框架效应可以改善理解，不能抹去信息：成功率与失败率、优惠与总成本、自动步骤与人工步骤应保持相同事实与分母。紧迫感只来自真实期限和条件。

## 交付前读一遍

目标用户能否说清“这与我何时有关、能得到什么、我需要做什么”？产品名拿掉后若完全看不出与其他产品的差异，补上真实机制或成果；已有清晰差异就不继续堆概念。每个数字、强承诺和权威身份可追溯；示例、规划和事实分别呈现。
