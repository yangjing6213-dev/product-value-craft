# 最小事实卡与验证

## 需要时共用一份事实依据

单条文案可在上下文中完成。多种素材、多人协作或长项目需要持久记录时，复用已有项目文档，或只建一份简短事实卡；不要另起平行的计划/产品定义。

```text
任务目标与本次交付：
人群、触发时刻、要完成的事：
目前替代办法与实际阻碍：
当前能力 / 信息来源与版本：
人工或外部步骤：
限制、依赖、总成本中已知的部分：
可展示的输入、过程、输出及素材状态：
拟议能力或待验证假设（不进入当前能力承诺）：
主要下一步与判断完成的证据：
```

字段用于防止混淆，不要求机械填满。事实来自用户陈述时注明依据层级；测试、来源文件和用户假设不能互换身份。关键资料未知时不填虚构数字、不将“未知”改写为“没有”。

## 一个贯通示例（虚构产品，仅展示方法）

事实：桌面工具“项目清单”可扫描用户选择的文件夹，导出文件名与路径CSV；不复制文件、不恢复项目。用户在其他程序查看清单。没有速度测试。

场景：准备把项目交给协作者，先核对要移交的文件。结果是可检查的文件清单，不是完整备份。

产品建议：优先确认排除项、扫描失败提示与导出结果是否一致；这些属于建议，尚不能宣传为已有功能。完成证据是样例目录的清单与已知内容逐项匹配，并清楚显示未处理项。

标题：项目清单｜交接之前，先核对文件。

短文案：选择项目文件夹，导出文件名与路径清单，供你检查交接内容。工具不会复制或恢复文件。

视频画面：选择文件夹 → 实际扫描结果 → 导出CSV → 用外部表格程序检查。缺少真实录屏时列为待提供素材，不生成假UI充当实测；无法证明速度时不用“瞬间完成”。

封面：文件夹与清单作为主视觉，标题“交接前，先核对”；不用“永不丢失”盾牌或“一键迁移”按钮。

插画：文件夹指向清单，再指向用户核对动作；不画清单自动变成已迁移项目。

这组表达共享任务与事实，但具体版式由渠道决定。本示例的工具、功能和流程不能自动套到真实项目。

## 验证重点

| 维度 | 要核对的问题 | 常见失败 |
| --- | --- | --- |
| 场景 | 用户在什么时刻需要它 | 用“所有创作者”替代真实任务 |
| 价值 | 能完成什么、比当前做法差在哪里 | 只堆“强大、高效、专业” |
| 证据 | 每个重要承诺依据是什么 | 用户描述变成“亲测”；作者例子变成自家数据 |
| 条件 | 适用范围、人工步骤、依赖与费用是否清楚 | 本地运行被说成绝对安全或永远离线 |
| 一致性 | 标题、文案、画面、流程和CTA是否相符 | 封面比正文多承诺一个自动化步骤 |
| 可交付 | 请求的产物是否真的存在、可打开/播放 | 以脚本代替成片并报告完成 |
| 范围 | 是否只执行当前授权任务 | 为改标题擅自开发功能或发布 |

按本次产物检查必要项，不向用户输出空泛评分。没有足够数据时报告具体可改问题，不报“营销评分98分”或保证提升比例。

## 运营观测与小实验

选择贴近目标的指标并写清分子、分母、去重口径、观察期及可见范围。曝光、点击、下载、安装、付款、成功使用是不同事件，不能互相代替。

若仅能从自愿反馈知道使用结果：已知结果中的成功比例 = 已知成功人数 /（已知成功人数 + 已知失败人数）。同时报告未知结果人数和反馈覆盖率；不要把未知算失败，也不要把有反馈者成功率称为全体用户成功率。必要时先改善观测，避免推断偏差。

少量目标用户试用能发现理解与操作问题，不足以证明总体转化提升。流量与测量条件允许时，再明确主指标、随机分配、观察窗口与停止条件做实验；避免因早期波动提前宣布获胜。事实错误应直接纠正，不把误导版本保留为对照。

实验/观察记录只需：改了什么、预期影响哪一步、实际观察、样本与缺失、下一步决定。没有结果就标待验证，不把候选方案自动写成长期事实。
