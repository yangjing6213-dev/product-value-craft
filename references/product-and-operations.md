# 产品策划、体验与运营

## 选择一个能完成的任务

把“做一款强大的工具”变成：某类人在某个触发时刻，需要把什么输入变成什么结果，当前如何做，哪里卡住。场景可以是工作、学习、生活或非商业项目，不必强行寻找购买焦虑。

规划新产品时，对少量可行场景比较：是否已有需求证据、发生频率与后果、替代办法、现有能力适配、接触用户的渠道、交付及支持成本。依据来自现有资料、实际观察或自愿反馈；缺证据的方向写成假设，不编造市场规模或给虚假的精确评分。

已有项目只处理当前改动的场景。用户要改一个按钮，通常只需确认按钮触发的行为、状态和后果。

## 把深度放进首次成功路径

检查“准备输入 → 满足前提 → 执行 → 确认结果 → 失败恢复 → 继续使用”。据实际问题选择改动，不要求每个项目重做全部环节。

| 问题 | 产品动作 | 可观察的验收 |
| --- | --- | --- |
| 用户不知道是否适合 | 显示输入格式、设备条件、用途与不适用情况 | 目标用户能判断自己能否使用 |
| 第一次卡在下载/配置 | 清楚说明准备过程、进度、错误与重试 | 可区分正在进行、已失败、需人工操作 |
| 结果无法判断是否完成 | 显示实际输出位置、预览或核验办法 | 能找到并检查约定交付物 |
| 失败后只能重新开始 | 给出与错误原因对应的恢复办法 | 能恢复或得到明确可执行的求助信息 |
| 营销与交付不一致 | 对齐事实说明、产品行为及售后范围 | 页面承诺可由现有版本复现 |

优先修复基本可用性、关键缺失与严重误解，再考虑惊喜功能。Kano等分类只是讨论辅助：同一功能对不同人群或阶段可能属于不同需求，不能永久定级。

功能建议写清“用户任务、当前障碍、拟改动、依赖/成本、完成证据”。不要把拟议路线图写入当前功能清单。设计和实现阶段继续遵循项目的开发技能；产品效果假设不能替代软件测试。

## 有依据地扩展广度

只在用户请求策划、探索或增长时考虑相邻机会：同一人群的前后步骤、相同能力的新场景、可复用的教程或服务。先推荐最有根据的方向，并写明何时值得验证；没有相关需求时停止扩张。

判断扩展是否值得：是否复用真实能力；用户能否理解它与原产品的关系；新增兼容、素材、支持与维护责任能否承担。“都使用AI”不足以成为捆绑依据。借鉴成熟结构和流程，不照搬别人的品牌、素材与性能承诺。

## 让运营位置承担不同任务

| 位置 | 应帮助用户完成的判断 |
| --- | --- |
| 搜索内容/标题 | 这是否回答了我此刻的问题 |
| 短视频/封面 | 这与我有什么关系，能看到什么真实结果 |
| 首页/目录 | 我该从哪个任务或产品入口开始 |
| 详情页 | 它是否适合我，与当前办法有什么可证差异 |
| 购买/注册区 | 得到什么、总成本、交付条件、下一步是什么 |
| 上手教程 | 如何完成第一次任务、卡住后怎么办 |
| 复访/社区 | 如何继续改进作品或完成相关任务 |

用任务入口帮助新用户，同时保留产品名、技术名和参数入口，照顾已经知道自己要找什么的人。外部内容指向匹配页面；不要在付款、下载等必要操作中插入无关广告或强制进群。

网站审查把“实际看到的页面信息、推断的影响、建议、验证方法”分开。静态文字检查不能证明交互故障；没有真实数据不报转化损失。先修正事实与流程矛盾，再研究文案表现。

观察首次成功、求助与重复使用，也收集流失者自愿表达的阻碍。沉默不等于不满；活跃评价不能代表全体用户。实验指标与口径见 [brief-and-checks.md](brief-and-checks.md)。
